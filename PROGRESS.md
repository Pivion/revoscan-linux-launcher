- Fixed the Pop!_OS Revo Scan no-window failure (0.1.2). Root cause: Wine's `winebth.sys` Bluetooth driver exposes the host BlueZ radio to Wine prefixes; Revo Scan's `simpleble.dll` then calls WinRT `BluetoothAdapter::FromIdAsync` / `DeviceInformation::CreateFromIdAsync`, which Wine still implements as `E_NOTIMPL` stubs (verified against Wine master). Radio-less behaviour is now enforced deterministically: the AppImage build strips `winebth.sys`/`winebth.so` from the bundled Wine, and the launcher's `sanitize_bluetooth` removes any staged `winebth.sys` plus the `Services\winebth` / `Enum\winebth` registry sections from existing prefixes before installer/launch. Verified on Pop!_OS 24.04 (COSMIC Wayland, RX 580) with the shipped 0.1.2 AppImage: a deliberately re-dirtied prefix was sanitized and Revo Scan 6.4.1.1088 launched with the full UI (1280x720 X11 window `IsViewable`, screenshot captured; `Scan plugin started` and all 15 plugins started; app logs `BluetoothManager init error` and continues). Bluetooth/BLE scanner discovery is therefore not available under this build until upstream Wine implements `DeviceInformation::CreateFromIdAsync`; WLAN-connected scanners are unaffected. Evidence preserved under git-ignored `local/pop-debug/`. New tests: `tests/test_bluetooth.py` (3); suite is now 26 Python unit tests plus the C suite.

## Accomplished (2026-11-05 session)

- **Working scanner connection (client mode, LAN):** Revo Scan 6.4.1 under bundled Wine connects to a POP4 (serial D26829775B6S00E1B) over the home LAN and streams DEPTH frames at ~78 fps. Recipe: (1) switch the scanner to Wi-Fi *Client* mode via Revo Scan over USB (About → Settings → Advanced Settings → Client; password must not contain spaces), (2) power it standalone so it joins the home network, (3) allow the scanner's IP through the host firewall — Fedora firewalld's public zone (only mdns/ssh/dhcpv6-client) silently dropped the scanner's UDP announcements (ports 8080 and the app's dynamic recv port); the app's sockets were bound and waiting but packets never arrived. `firewall-cmd --add-rich-rule='rule family="ipv4" source address=<scanner-ip> accept'` (runtime + permanent) fixed discovery instantly.
- **Working GPU identity mapping under Wine (verified end-to-end):** with `build_revoscan_environment` output (VK_LAYER_PATH → bundled layer dir, VK_INSTANCE_LAYERS, REVOSCAN_MAP_*), the host Linux loader chains `VK_LAYER_REVOSCAN_LINUX_GPU_MAP` inside the Wine process and Revo Scan's own Vulkan enumeration reports `#0 AMD Radeon RX 7700 XT` instead of the real Intel 8086:fd80. Earlier "Wine does not chain layers" conclusion was wrong — the failures were test-harness bugs: (a) mapping env vars set but not exported never reached Wine (layer silently disabled), (b) a stale Windows-style `VK_LAYER_PATH` (`Z:\...`) from Wine-registry experiments shadowed default layer search paths so the loader "found no files".
- Host-side verification: `vulkaninfo --summary` with the mapping env reports `vendorID = 0x1002, deviceID = 0xfd80, DISCRETE_GPU`. `--vulkan-check` CLI diagnostic now detects whether mapping actually applied and prints a verdict plus a firewall/layer-path hint on failure.
- **AP mode also confirmed firewall-caused:** with `firewall-cmd --add-rich-rule='rule family="ipv4" source address="192.168.179.0/24" accept'` (runtime + permanent) added for the scanner's AP subnet, AP-mode discovery and streaming work immediately from the dual-adapter host (dongle on `scanner-static` static profile): probe → `push to list` → `Camera::connect` → DEPTH/RGB frames (~7 fps over the dongle link; client mode over 5 GHz home Wi-Fi reached ~78 fps — prefer client mode for throughput). Earlier AP-mode failures on this same setup were entirely the firewalld public zone dropping inbound UDP.
- Device behavior notes: (1) **USB-connected scanners kill their own Wi-Fi data path** — AP associates (−34 dBm) but passes no traffic until USB is unplugged and the device power-cycled; (2) scanner **AP mode + dual-adapter hosts** needs the AP subnet allowed through the host firewall (see above); **client mode on the same LAN as the app is the higher-throughput path** and matches the user's known-good "lan + wlan" machine setup; (3) the USB dongle's Wi-Fi profile must be `never-default` so the device subnet never hijacks the host default route.

## Accomplished (2026-11-06 session)

- **Scanner Wi-Fi selection removed.** The launcher no longer runs `nmcli` scans or connects adapters: the user attaches the spare Wi-Fi adapter to the scanner's access point in the desktop's network settings (host-mode workflow). `network.py` now only deals with host firewalling — IPv4 link/subnet detection (`ip -o -4 addr`), default-route exclusion, CIDR-normalised firewalld rich rules, a `FirewallReport` status object and idempotent runtime+permanent rule creation.
- **Firewall punch-through button + status in the GUI.** Section "2 · Scanner network" auto-fills the spare interface's subnet (e.g. `192.168.179.0/24` on the dongle), offers an editable field for manual IP/CIDR, an *Allow through firewall* button and a status line that reports firewalld state, existing allowances, missing rules, or the exact `sudo` command when elevation is unavailable. Verified on this host: status reported `firewalld already allows 192.168.179.0/24` with the dongle attached.
- **GPU mapping root-caused on this machine.** Two independent defects: (a) the layer manifest declared `"library_path": "librevoscan_gpu_map.so"` without `./`, so the Vulkan loader treated it as a system library name and `dlopen` failed (confirmed with `VK_LOADER_DEBUG`: `cannot open shared object file`); (b) the extracted per-user runtime (`~/.local/share/revoscan-linux-launcher/appdir`) still held a 2026-10-17 build of the layer that preserved the source device ID, so Wine reported `1002:fd80` instead of the target `1002:7480`. `runtime.py` now sets `VK_LAYER_PATH` only when the directory holds both manifest and library (`mapping_layer_dir()`), otherwise it launches unmapped and says so. The manifest is fixed, the layer rebuilt, and Wine verified again: `[revoscan-gpu-map] Vulkan identity 8086:fd80 'Intel(R) Graphics (WCL)' -> 1002:7480 'AMD Radeon RX 7700 XT'` inside the Revo Scan process.
- **GUI mapping diagnostics.** The GPU box shows whether the layer is available and adds a *Verify mapping…* button that runs `vulkaninfo` with the exact mapping environment and prints the reported identity plus an applied/not-applied verdict (`check_vulkan_identity` now accepts an explicit source/target).
- **Revo Scan's GPU check reads DXGI, not Vulkan — fixed by switching wined3d's renderer.** `RvGPUUtils::getDiscreteGpuInfo` logs "Vulkan EnumerateVulkanDevices" but enumerates **DXGI** adapters. With Wine's default GL-backed wined3d it saw a synthesised `Intel(R) HD Graphics 4000`, PCI 8086:0162, 1.5 GiB (`amdDiscrete=no` → "no AMD discrete Vulkan device after filter", foreground segmentation skipped). Wine 11 ignores the `VideoPciVendorID`/`VideoPciDeviceID`/`VideoDescription` values the earlier launcher wrote (verified with a mingw DXGI probe: identity stayed Intel 8086:0162 with the keys present). Setting `HKCU\Software\Wine\Direct3D\renderer=vulkan` makes wined3d read the Vulkan physical-device properties instead, which the layer already rewrites: the DXGI probe then reports `AMD Radeon RX 7700 XT`, vendor 0x1002, device 0x7480, 11.4 GiB. `set_wine_gpu_override` now selects the Vulkan renderer and `clear_wine_gpu_override` removes it (plus the dead legacy keys). Verified through the GUI: Revo Scan logs `D3D11: "AMD Radeon RX 7700 XT"`, Ogre's Vulkan render system lists `#0 AMD Radeon RX 7700 XT`, and `selected Vulkan device index=0, name=AMD Radeon RX 7700 XT` — with the scanner streaming DEPTH at 78 fps in the same run.
- **Firewall probe is user-initiated only.** Opening the launcher no longer queries firewalld (its D-Bus calls can trigger a polkit password prompt). The status line starts as "Click ‘Check status’…"; the button is now labelled *Check status*, and *Allow through firewall* auto-detects the spare-interface subnet when the field is empty using `ip` only.
- `python -m revoscan_launcher` now routes through `entrypoint.run()`, so `--vulkan-check` / `--check-wine` work from a source checkout instead of silently starting the GUI.
- Tests: 58 Python unit tests (Wi-Fi scan/connect tests replaced by link detection, `FirewallReport`, GUI firewall/mapping-state and wined3d-renderer override tests) and the C mapping suite pass; the C test file was stale against the 6-argument `parse_gpu_map` and now covers target-device spoofing.

- Resolve/characterize the Fedora 44 container WineBoot smoke timeout and test on a full Fedora desktop with host graphics libraries.
- Investigate the Revo Scan no-window failure on Pop!_OS. Fresh-prefix runs under bundled Wine 11.0, system Wine 9.0, and manual Wine Staging 11.0 reproduce it. Live `+seh` evidence shows a `winrt::hresult_not_implemented` exception whose RTTI is in `simpleble.dll` during plugin activation, followed by a generic `ctkRuntimeException` (`ctkPlugin start failed`). `simpleble.dll` contains Windows C++/WinRT Bluetooth initialization code, and `rvscan.dll` exposes Bluetooth-manager initialization. I initially treated this as causal, but the working Fedora log also records `BluetoothManager init error` despite no Bluetooth adapter and later proceeds to POP4 streaming. A GDB breakpoint also hit CTK's generic `ctkPlugin start failed` catch-all constructor, whose overload does not retain an inner exception. The preceding SimpleBLE/WinRT `hresult_not_implemented` is therefore correlation, not proof of cause; the fatal `rvscan` startup cause remains unknown. Ghidra confirms `ScanPlugin::start` logs `Scan plugin started` only at its end, and Pop logs stop immediately after `Starting plugin: rvscan`. The app never sends a show/map request for its top-level window. `rvcore` provides the camera-manager service queried by `rvscan` and starts first, so simple missing-service ordering is not supported. Bundled-Wine Notepad maps normally. Forced X11, virtual desktop, software OpenGL, and X11 remapping did not produce usable UI; forced mapping yielded black. No reliable workaround is confirmed. Environment comparison: the AppImage SHA-256 matches on both hosts (`b12e8444387dd0336dafcefc62f76f2705b654d1d4971ce1f76ee3ff3e310d4c`). Fedora is Ultramarine 44/KDE Wayland, kernel 7.2.9, Mesa 26.2.4, Xwayland 24.1.14, Radeon 780M; Pop is 24.04/COSMIC Wayland, kernel 7.1.5, Mesa 26.1.6, Xwayland 24.1.13, RX 580. The launcher inherits host variables; Pop session processes export `QT_QPA_PLATFORM=wayland;xcb` and `GDK_BACKEND=wayland,x11`, unlike Fedora's session. A disposable-prefix run with the Pop `QT_QPA_PLATFORM` value still failed at `rvscan`; X11 window creation varied between runs, so this variable is not isolated as the cause. The user's systemd user-manager environment points to XRDP X11 `DISPLAY=:10.0`, while the COSMIC Wayland session is `:1`. Under identical Wine 11/prefix/environment except `DISPLAY`, `:1` starts the OpenGL 3+ renderer and reaches `rvscan`; `:10.0` stops in `MainWindow::initVisualMgr`. Its `ogre.log` ends after OpenGL subsystem creation, and the Wine trace reports `X Error: BadValue` from `XFree86-VidModeExtension` request `XF86VidModeSetGamma`. This strongly implicates the XRDP gamma-ramp path for launches on `:10.0`; the exact caller is not yet identified. The `:1` run still has a separate `rvscan` activation failure. In the disposable prefix, setting Wine `HKCU\\Software\\Wine\\X11 Driver\\UseXVidMode` to `REG_SZ N` on `:10.0` removed the `XF86VidModeSetGamma` BadValue, let Ogre start OpenGL 3+, and let `rvcore` start; `rvscan` still failed to complete and no usable window appeared. The test value was deleted and verified absent. This confirms the XRDP gamma error is one environment blocker, not the whole fix. A related xorgxrdp report documents the same BadValue request: https://github.com/neutrinolabs/xorgxrdp/issues/271. **RESOLVED (2026-10-17, see Accomplished): the root cause was Wine's `winebth` Bluetooth driver exposing the host BlueZ radio; removing it from the bundled runtime fixed the failure.**

## Known issues and limitations
- Fedora 44 container testing timed out during WineBoot; this is not a pass. openSUSE and Arch are untested.
- The Debian 12 test had no Vulkan driver; it cannot validate GPU mapping or scanning.
- Intel-to-AMD identity mapping is unverified on physical Intel hardware. A successful identity-filter check does not guarantee compute support.
- No complete Revo Scan scan/fusion/export has been completed. The Pop!_OS no-window failure was root-caused and fixed in 0.1.2: Wine's `winebth` Bluetooth driver exposed the host BlueZ radio and Revo Scan's `simpleble.dll` hit still-stubbed WinRT Bluetooth APIs (`E_NOTIMPL`) during `rvscan` plugin activation, killing the app before its window mapped; the build now strips the driver from the bundled Wine and the launcher sanitizes prefixes. Bluetooth/BLE scanner discovery does not work under this build until upstream Wine implements `DeviceInformation::CreateFromIdAsync` (Wine master still stubs it); WLAN-connected scanners are unaffected. The XRDP gamma `XF86VidModeSetGamma` BadValue on `DISPLAY=:10.0` (https://github.com/neutrinolabs/xorgxrdp/issues/271) is a separate environment blocker for XRDP sessions; launches on the COSMIC Wayland session (`:1`) work.
- The final AppImage is a preview build, not a published release. It uses the host graphics stack and device permissions.
